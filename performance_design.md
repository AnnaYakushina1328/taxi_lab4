# Домашнее задание 05: Оптимизация производительности через кеширование и rate limiting

Вариант 16: Система заказа такси.

## 1. Контекст системы

В работе рассматривается REST API сервиса заказа такси.

Основные сущности:

- пользователь;
- водитель;
- поездка.

Основные операции:

- создание нового пользователя;
- поиск пользователя по логину;
- поиск пользователя по маске имени и фамилии;
- регистрация водителя;
- создание заказа поездки;
- получение активных заказов;
- принятие заказа водителем;
- получение истории поездок пользователя;
- завершение поездки.

## 2. Анализ производительности

### 2.1. Hot paths

К часто вызываемым операциям относятся:

| Endpoint | Причина частого вызова |
|---|---|
| GET /users?login=... | часто используется для поиска пользователя и проверки существования логина |
| GET /users?name_mask=... | используется для поиска пользователей по имени |
| GET /rides?status=active | часто вызывается водителями для получения списка доступных заказов |
| GET /rides?user_id=... | часто вызывается пользователями для просмотра истории поездок |

### 2.2. Потенциально медленные операции

Потенциально медленными являются:

- обращения к PostgreSQL;
- поиск пользователей по текстовым полям;
- получение активных заказов;
- получение истории поездок пользователя;
- создание заказа поездки;
- принятие заказа водителем;
- завершение поездки.

Операции с поездками могут быть медленными, потому что они меняют статус заказа и требуют согласованности данных.

### 2.3. Требования к производительности

| Метрика | Целевое значение |
|---|---|
| Время ответа при cache hit | до 20 мс |
| Время ответа при cache miss | до 100 мс |
| Время ответа write-операций | до 200 мс |
| Пропускная способность GET /rides?status=active | 100 запросов в минуту |
| Доля успешных запросов при нормальной нагрузке | не менее 99% |

## 3. Стратегия кеширования

### 3.1. Кешируемые данные

| Endpoint | Ключ кеша | TTL | Причина |
|---|---|---|---|
| GET /users?login=... | users:login:{login} | 60 секунд | данные пользователя часто читаются и редко меняются |
| GET /users?name_mask=... | users:name_mask:{mask} | 60 секунд | поиск по имени может нагружать БД |
| GET /rides?status=active | rides:active | 15 секунд | активные заказы часто читаются водителями |
| GET /rides?user_id=... | rides:history:{user_id} | 60 секунд | история поездок часто просматривается пользователем |

### 3.2. Выбранная стратегия

Используется стратегия Cache-Aside / Lazy Loading.

Алгоритм:

1. Сервис получает GET-запрос.
2. Сначала проверяется кеш.
3. Если данные есть в кеше и TTL не истёк, ответ возвращается из кеша.
4. Если данных нет, сервис обращается к PostgreSQL.
5. Ответ из БД сохраняется в кеш.
6. Клиент получает ответ.

Эта стратегия выбрана потому, что она простая, хорошо подходит для REST API и не требует изменения схемы базы данных.

### 3.3. TTL

Для пользователей выбран TTL 60 секунд, потому что эти данные меняются редко.

Для активных заказов выбран короткий TTL 15 секунд, потому что список доступных поездок быстро меняется.

Для истории поездок выбран TTL 60 секунд, потому что история меняется только при создании или завершении поездки.

### 3.4. Инвалидация кеша

| Операция | Что инвалидируется | Причина |
|---|---|---|
| POST /users | users: | новый пользователь может изменить результаты поиска |
| POST /drivers | drivers: | новый водитель может изменить данные по водителям |
| POST /rides | rides: | появился новый активный заказ |
| PATCH /rides/{id}/accept | rides: | заказ перестал быть активным |
| PATCH /rides/{id}/complete | rides: | изменилась история поездок и статус заказа |

## 4. Реализация кеширования

Кеш реализован в памяти процесса приложения.

Файл реализации:

- src/performance/simple_performance.hpp

Особенности реализации:

- потокобезопасность через std::mutex;
- хранение готового JSON-ответа;
- TTL для записей кеша;
- инвалидация по префиксу;
- подсчёт cache hits и cache misses.

В ответ добавляется заголовок:

- X-Cache: MISS — данные получены из БД;
- X-Cache: HIT — данные получены из кеша.

## 5. Проектирование rate limiting

Rate limiting нужен для endpoint-ов, которые часто вызываются и могут создать большую нагрузку на БД.

В рамках работы rate limiting применяется к endpoint-у:

- GET /rides?status=active

Этот endpoint часто вызывается водителями, которые ищут доступные заказы.

### 5.1. Алгоритм

Выбран алгоритм Fixed Window Counter.

Причины выбора:

- простая реализация;
- понятная логика;
- подходит для учебного проекта;
- не требует внешнего хранилища.

### 5.2. Лимит

Для GET /rides?status=active задан лимит:

- 100 запросов в минуту.

При превышении лимита возвращается:

- HTTP 429 Too Many Requests.

Также возвращаются заголовки:

- X-RateLimit-Limit;
- X-RateLimit-Remaining;
- X-RateLimit-Reset;
- Retry-After.

## 6. Влияние на производительность

Кеширование уменьшает количество одинаковых запросов к PostgreSQL.

Положительный эффект:

- уменьшается среднее время ответа;
- уменьшается нагрузка на базу данных;
- повторяющиеся поисковые запросы обслуживаются быстрее;
- водители быстрее получают список активных заказов.

Rate limiting защищает сервис от избыточного количества запросов.

Положительный эффект:

- один клиент не может бесконечно нагружать endpoint активных заказов;
- снижается риск перегрузки сервиса;
- API возвращает понятный статус 429;
- клиент получает заголовки с информацией о лимите.

## 7. Метрики мониторинга

| Метрика | Назначение |
|---|---|
| cache_hits | количество успешных обращений к кешу |
| cache_misses | количество промахов кеша |
| cache_hit_rate | доля ответов из кеша |
| request_latency_ms | время ответа endpoint-а |
| db_query_count | количество запросов к PostgreSQL |
| http_429_total | количество заблокированных запросов |
| rate_limit_remaining | оставшееся число запросов в текущем окне |

## 8. Как измерить эффективность кеширования

Эффективность кеширования измеряется через hit rate:

hit rate = cache hits / (cache hits + cache misses)

Пример:

cache hits = 80

cache misses = 20

hit rate = 80 / (80 + 20) = 0.8 = 80%

Чем выше hit rate, тем больше запросов обслуживается без обращения к PostgreSQL.

## 9. Ограничения текущей реализации

Текущая реализация подходит для учебной работы, но имеет ограничения:

- кеш хранится только в памяти одного процесса;
- при перезапуске приложения кеш очищается;
- при нескольких инстансах сервиса у каждого будет свой кеш;
- rate limiter также хранится в памяти одного процесса.

Для промышленной эксплуатации лучше использовать Redis.
